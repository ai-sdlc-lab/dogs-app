# PLAN-0004: Invalid input returns 422 with the standard error body and is logged as `input.rejected`

<!-- Stage 3, derived from SPEC-0004, TRACE-0004 and THREAT-0004. One repo (dogs-app), one code PR. -->

## Order of work

1. A-01 request ID helper (shared by 503 and 422).
2. A-02 `rejected()` and the log writer, plus the framework-validation handler. No route changes yet, so nothing is red in between: the tests drive a test-only route with a typed parameter.
3. A-03 route change: whole-value breed rule, the route calls `rejected()`, listing re-check. Needs A-01 and A-02.
4. A-04 build info target and `version`. Needs only A-02 (the writer reads the file); may be done any time after it.
5. A-05 architecture doc update, then the final gate (`make test`, `make lint`).

Design (fits `docs/architecture.md`: one FastAPI app on Lambda, stdout logs to CloudWatch, no new service):
- `api/app/main.py` keeps routes, handlers and the `security_headers` wrapper. The wrapper is the outermost layer, so the 422 gets the SR-004 headers with no extra code (M-10).
- New `api/app/rejection.py` holds the request-ID helper, `rejected()` and the log writer.
- Request ID: `request.scope["aws.context"].aws_request_id`, else `secrets.token_hex(16)` (32 lowercase hex, 128 bits, CSPRNG). No header or query value is read. `uuid` is no longer used.
- Log writer: the whole body (request-ID lookup, source-IP lookup, version read, dict building, `json.dumps`, `print`) is inside one `try/except Exception`. A failure anywhere writes nothing and never reaches the response (M-08). The request ID used in the response is computed outside the `try` by the request-ID helper, which cannot raise: the scope lookup is wrapped in its own `try/except Exception`, and a missing `aws.context`, a context without `aws_request_id`, or an ID that is not a non-empty `str` all fall back to the 32-hex ID. The body ID always equals the logged ID.
- Source IP: `request.scope["aws.event"]["requestContext"]["http"]["sourceIp"]`, else `unknown`. No header is read.
- Breed rule: `BREED = re.compile(r"[a-z0-9-]{1,40}")` used with `fullmatch` in the route and in `list_dogs`. Validation happens before `list_dogs`, so no S3 call is made for a rejected breed (M-09).
- Version: a small Makefile target writes `build_info.json` into the Lambda package; the writer reads it beside `rejection.py`; missing or unreadable gives `unknown`.

Step details:
- A-01: `request_id(request)` in `rejection.py`; `s3_unavailable` in `main.py` calls it. `test_request_id_survives_malformed_aws_context` (M-05, M-08) sends a rejected request with `aws.context` absent, with a context object lacking `aws_request_id`, with `aws_request_id` set to a non-str (`None`, an int, an object) and with a context whose attribute access raises; each case returns the 422 with a 32-hex `request_id` equal to the logged one and no trace. `test_503_request_id_generated_when_missing` (in `test_s3_503.py`) changes from UUID v4 to 32 lowercase hex.
- A-02: `rejected(request, reason)` calls the log writer, then returns `JSONResponse(422, {"error": "invalid_input", "request_id": id})`. `api.add_exception_handler(RequestValidationError, ...)` uses it with reason `invalid_request`, so the default framework body is never sent. The writer builds exactly the 7.2 keys: `ts` (UTC, milliseconds, `Z`), `http.path` from `request.url.path` cut to `[:200]` (never the query string), `http.method` from `request.method`, `service` `dogs-app`. Output is `print(json.dumps(event), flush=True)`; `ensure_ascii` escapes newline, control and non-ASCII characters, so it is one line. Tests here use a test-only route with a typed `int` parameter on a locally built app, with hostile paths such as `/t/x%0A%22`. `test_rejected_still_422_when_log_write_fails` has two cases: (a) patch only `print` and `json.dumps` (not the writer) to raise; (b) make event building raise (the version read patched to raise). Both expect the same 422, body and headers and no trace. M-12 (cost bound, no alarm test) is implemented by the `[:200]` cap and proven by `test_rejected_log_path_truncated_to_200`; the alarm stays with #38. SR-023 and SR-025: the writer only prints to stdout, so the event goes to the existing log group, and `test_rejected_logs_input_rejected_event` (exact key set) proves nothing else is logged.
- A-03: the route calls `rejected(request, "invalid_breed")` for a bad breed (no more `HTTPException(404)` for it) and keeps `404 {"detail": "unknown breed"}` for a valid breed without images. `list_dogs` uses `BREED.fullmatch` on the key's breed segment. Test edits: `test_malformed_breed_404_without_s3_call` becomes `test_dogs_by_breed_rejects_without_s3_call`; `test_unknown_or_invalid_breed_is_404` keeps only `husky` as `test_unknown_valid_breed_stays_404` (`test_api.py`); the `Bad_Breed` row of `test_security_headers` (`test_headers.py`) expects 422; `test_listing_skips_key_with_trailing_newline` is added in `test_api.py`.
- A-04: new Makefile target `build-info` with variable `BUILD_INFO ?= build/lambda/app/build_info.json`. It runs `mkdir -p $(dir $(BUILD_INFO))` and writes `{"sha": "<git rev-parse HEAD>"}` to that path; it needs only git (no npm, no pip). `make build` calls `$(MAKE) build-info` after `cp -R api/app build/lambda/app` and before `zip`. `test_build_zip_contains_build_info` (`api/tests/test_build_info.py`) runs `make build-info BUILD_INFO=<tmp>/build_info.json` and checks the file holds a 40-hex SHA equal to `git rev-parse HEAD`; it also reads `make -n build` and checks that the `build-info` call comes after the `cp -R api/app` line and before the `zip` line, so the SHA is in the zip. `make test` (target `test-api`) runs this test, so M-11 is in the gate and no npm or pip is needed. `test_rejected_log_version_from_build_info` writes a temporary `build_info.json`, checks `version` equals its SHA, then removes it and checks `unknown`. The file lives only under `build/` (already in `.gitignore`).
- A-05: update `docs/architecture.md`: the API now has a `422` `invalid_input` path with the fixed body; one `input.rejected` JSON line per rejected request goes to stdout and CloudWatch; the fallback request ID is 32 lowercase hex characters (remove the UUID statement); rewrite the "not logged yet" sentence to "Only rejected input (422, `input.rejected`) is logged; S3 failures (503) and other errors are not logged yet (#38)"; adjust the Known gaps SR-024 line to the built behaviour (only the `input.rejected` event exists; the other mandatory events stay with #38); `build_info.json` with the git SHA is in the Lambda zip; the header becomes "as of change 0004". SR-006 and SR-007 are unchanged and stay proven by the three existing tests listed.

## Test plan

- Every test is owned by exactly one step (the Tests column). New tests are in `api/tests/test_invalid_input.py` unless the step says otherwise: `test_api.py` (A-03), `test_headers.py` (A-03), `test_s3_503.py` (A-01, A-03), `test_build_info.py` (A-04).
- Log tests capture stdout with `capsys` and parse each line with `json.loads`. The hostile-path test compares the parsed `http.path` with the expected decoded path. The source-IP test sets `scope["aws.event"]` in the Mangum event shape and also sends `X-Forwarded-For`.
- Existing tests that keep passing unchanged: `test_health_ok_when_s3_failing` and the ones named in A-05.
- Gate: `make test` (includes the build-info test) and `make lint` (ruff check and format check).
- `crosscheck.py TRACE THREAT PLAN` must pass: every covered SR and every M-xx is in the Implements column of a step with named tests.

## Infrastructure and IAM changes

None. No Terraform, IAM, workflow or dependency change. The log group, 7-day retention and AWS-managed encryption are unchanged (SR-023, SR-024 lab exceptions). The build change is the `build-info` target in `Makefile` (A-04).

## Rollout and rollback

- Rollout: merge to `main`; CI deploys the Lambda zip (owner approval at the `main` merge). Nothing to migrate. The web app needs no change.
- Check after deploy: `GET /api/dogs/Bad_Breed` returns `422` with `{"error":"invalid_input","request_id":...}` and one `input.rejected` line appears in the function's log group with `version` equal to the deployed commit SHA.
- Rollback: redeploy the previous commit (revert the PR). Behaviour returns to `404` for malformed breeds and the UUID fallback ID. No data or infrastructure to undo.
