# INT-0004: Invalid input returns 422 with the standard error body and is logged as `input.rejected`

## Problem
GitHub issue #65 (finding SR-001, severity medium, old debt carried over from change 0003): requirement SR-001 (input validation) says a request that fails validation returns `422` with the SR-005 error body and is logged as `input.rejected` (SR-024). Today this is not met:

- `GET /api/dogs/{breed}` accepts a breed only if it matches `^[a-z0-9-]{1,40}$`. A malformed breed (for example `Bad_Breed`, `..`, or 41 characters) is answered with `404` and the body `{"detail": "unknown breed"}`, not `422`.
- A well-formed breed that has no images (for example `husky`) gets the same `404` and body.
- Nothing is logged in either case: the API writes no log events at all today, so a rejected input leaves no trace for the owner.
- The `404` body is not the SR-005 body `{"error": "<code>", "request_id": "<id>"}`. Only the `503` for S3 failure (change 0003) uses that body.

Why now: it is an open finding in the issue tracker; the owner wants the debt closed. Related: #30 (SR-005 error body for 4xx and 500 in general) and #38 (SR-024 log format and events in general). This change only covers the validation-failure case and must not wait for them.

## Users and actors
- Visitors of the dog gallery and any other API caller: send the breed in the URL; they get a clear "invalid input" answer for a malformed breed.
- The owner / operators: can see in the logs that, and how often, invalid input was sent, and tell it apart from a missing breed.
- The web app (calls `/api/dogs/{breed}`): receives a different status for malformed breeds.

## What changes
### Functional
Applies to every external input of the API. Today the only validated input is the `breed` path value of `GET /api/dogs/{breed}`; `/api/dogs` and `/api/health` take no input.

1. A breed that does not match the existing rule (1 to 40 characters, only `a-z`, `0-9`, `-`) is rejected with status `422` and the body `{"error": "invalid_input", "request_id": "<id>"}`. The rule itself does not change. No S3 call is made for a rejected breed (as today).
2. The body contains no exception text, field name, submitted value, path or library detail. `request_id` is the Lambda request ID, or a generated UUID if it is missing (same as the `503` of change 0003).
3. Any other failure of the framework's own request validation also gives this `422` and body, so the framework's default `422` body (which lists the submitted value and field) is never sent.
4. Every rejected input writes one log event `input.rejected` with the SR-024 mandatory fields: `ts`, `level`, `event`, `outcome` (`failure`), `request_id` (the same value as in the response body), `actor` (`anonymous`: the API has no login), `source_ip` (from the platform request context, never from `X-Forwarded-For`), `http` (`method`, `path`, `status` 422), `reason` (`invalid_breed`), `service`, `version`. `http.path` holds the actual request path without the query string, truncated to 200 characters. The log line is JSON-encoded by the logger, so newline, control and quote characters in the path cannot forge or break entries. The submitted value may appear in the log only in this field; never in the response.
5. A well-formed breed with no images keeps `404` (a missing resource is not invalid input; decided). Its body and the unknown-route `404` bodies are not changed here (that is #30).
6. Success responses, `503` responses, `/api/health` and all SR-004 security headers stay as today. The `422` carries the same SR-004 headers as every other response.

### Visual
None. (The web app may show whatever it already shows for a failed API call; no new screen or text is requested.)

## Data handled
| Data | Source | Personal/sensitive? | Kept for |
|---|---|---|---|
| Submitted breed value (path segment) | The caller | Untrusted, not personal; may be anything an attacker sends | Validated per request; not stored except inside the logged request path (next row) |
| Request path (no query string, at most 200 characters) | The caller | Caller-controlled and untrusted; not personal data | In the log event, 7 days |
| Request ID, method, status, reason code | Platform request context / fixed by the API | No personal data | In the log event, 7 days |
| Source IP address | Platform request context | Personal data under many privacy regimes | In the log event, 7 days (the SR-024 lab exception). Purpose: security monitoring (spotting and tracing repeated hostile input); used for nothing else |
| Error response (`error` code, `request_id`) | Generated by the API | No | Not stored by this change |

## Trust assumptions
- Callers are untrusted: every byte of the URL may be hostile. Nothing from the request is copied into the response body or a header.
- The request path is untrusted. It is logged only as a JSON-encoded, length-capped (200 characters) string value, so it cannot forge or break log entries or grow a log line without bound. The query string is never logged.
- The platform request context (Lambda request ID, source IP) is trusted; `X-Forwarded-For` is not.
- Where the logs go (the Lambda log group on stdout) is existing infrastructure. No new dependency or AWS service.

## Out of scope
- The fixed SR-005 body for every other 4xx, for `404` and for `500`, the last-resort handler and `error.unhandled` logging (#30).
- The full SR-024 logging setup and all other mandatory events, log retention and log access rules (#38). This change adds only `input.rejected`, with the SR-024 field format, so #38 can reuse it.
- Rate limiting, request size limits and new validation rules (the breed rule is unchanged).
- Changes to the web app and infrastructure.

## Success criteria
1. For each malformed class (uppercase or underscore such as `Bad_Breed`, `..`, 41 characters, a non-ASCII character), `GET /api/dogs/<value>` returns `422` with a body that is exactly `{"error": "invalid_input", "request_id": "<id>"}`, `request_id` non-empty. Tests named `test_*_rejects_*` (SR-001 evidence) assert this per rejected class.
2. The `422` body contains none of the submitted value, field names, the word `detail`, or any exception text.
3. No S3 call is made for a rejected breed; a test asserts it.
4. For each rejected request exactly one `input.rejected` log line is written, as one JSON object with all fields of change item 4, `outcome` `failure`, `reason` `invalid_breed`, `http.status` `422`, a `request_id` equal to the one in the response body; a test asserts the fields.
5. `http.path` is the actual request path: tests assert that (a) for newline, control, quote and non-ASCII characters in the breed the log line is one valid single-line JSON object that parses back to the exact path; (b) a path longer than 200 characters is truncated to 200 characters; (c) a request with a query string logs a path without it and the query string appears nowhere in the line; (d) the response body still never contains the submitted value.
6. A well-formed unknown breed (for example `husky`) still returns `404`, and a found breed, `/api/dogs` and `/api/health` return what they return today. The existing tests that expect `404` for malformed breeds are changed to `422` in the same change.
7. The `422` response carries the same SR-004 security headers as other responses.
8. `make test` and `make lint` pass.

## Decided
1. A well-formed breed with no images (`husky`) stays `404`: SR-001 covers validation failures and that input is valid.
2. `http.path` in the `input.rejected` event is the actual request path without query string, JSON-encoded by the logger and truncated to 200 characters, as SR-024 asks.
3. The `422` body error code is `invalid_input`; the log `reason` is `invalid_breed`.
4. Source IP is logged for security monitoring and kept 7 days (the SR-024 lab exception).
