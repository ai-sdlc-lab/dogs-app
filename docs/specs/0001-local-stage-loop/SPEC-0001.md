## 1. Behaviour

### 1.1 Starting and running a change
- The owner starts a Claude Code session **in the product repo** (dogs-app), so that repo's `.claude/settings.json`, hooks and agents apply.
- `/stage intent <idea>` starts a change. The session picks the next free number `NNNN` (highest folder number under `docs/specs/` + 1), derives `<slug>` from the idea (lowercase kebab-case, `^[a-z0-9]+(-[a-z0-9]+)*$`, 3–40 characters, at most 5 words; the owner may override it in the command as `/stage intent <slug>: <idea>`), creates `feature/<NNNN>-<slug>` and folder `docs/specs/<NNNN>-<slug>/`, and pushes the branch.
- Pre-flight, before any stage: the appsec-baseline checkout matches the lock and is clean (M-09); `aws sts get-caller-identity --profile sdlc-lab-admin` must fail, otherwise `/stage` stops and asks the owner to run `aws logout --profile sdlc-lab-admin` (M-04); arguments pass validation (M-15).
- The session then runs stages `intent → spec → plan → code` in order without further owner input, except for questions (1.4) and SR decisions (1.5). `/stage <stage> <NNNN>` re-runs one stage; "next stage" continues an interrupted change.
- Per stage: branch `stage/<NNNN>-<stage>` from the feature branch → author → reviewers → gate → fix loop → commit → PR into the feature branch → CI green → the session merges the PR → next stage.
- After the code stage: PR `feature/<NNNN>-<slug>` → `main`. The session opens it and stops. Only the owner approves and merges it.

### 1.2 Stage definitions (`stages.yml`, repo root)

| Stage | Author output | Reviewers (in order) |
|---|---|---|
| intent | `INT-<NNNN>.md` | intent-completeness, security-requirements-auditor |
| spec | `SPEC-<NNNN>.md` | spec-completeness, security-requirements-auditor (returns the content of `TRACE-<NNNN>.md`), security-architect (returns the content of `THREAT-<NNNN>.md`); the main session writes both files |
| plan | `PLAN-<NNNN>.md` | architecture-conformance, security-architect; script `crosscheck` |
| code | code + tests (+ `PLAN-<NNNN>.md` if the work departs from it) | security-code-reviewer; workflow-iac-reviewer if a changed path matches `^(\.github/\|infra/)`; scripts `named-tests`, `plan-drift` |

`stages.yml` lists per stage: template, author agent, reviewers, scripts, `max_rounds: 3`. CI reads `stages.yml` **from the PR's base branch**, never from the PR head.

### 1.3 Fix loop
- Round = author writes or revises → each reviewer runs → `validate` → `gate`.
- Gate result per round: **allow** (no open findings) → commit; **block** (author-fixable findings) → next round with the findings; **questions** (`needs_human: true`) → ask the owner (1.4); **escalate** (any SR finding without a valid exception, or a prompt-injection finding) → ask the owner (1.5).
- After round 3 with findings still open: the session stops the change and shows the owner the open findings.
- The author may fix structure, derivable detail and testability. It never invents product facts, never decides an SR finding, never sets `accepted-risk`.

### 1.4 Questions
Shown in the session as: what is missing, why it matters, the options. The owner's answer is written into the artifact and recorded in the stage report (`resolved_by: owner`).

### 1.5 SR findings (owner decides)
- Any finding whose `sr_ref` is `SR-xxx` → escalate, whatever its severity or `blocking` value.
- The owner chooses **fix** (the author fixes it in the next round) or **accept**: the session prepares an entry in appsec-baseline `exceptions/sr-exceptions.yml` (2.4) as a PR there; the finding's status becomes `accepted-risk` only once that PR is merged by the owner.
- An expired exception doesn't match; the finding escalates again.

### 1.6 Reports
After the gate allows, the session writes one file per reviewer: `docs/specs/<NNNN>-<slug>/reviews/<STAGE>-<NNNN>.<reviewer>.json` (format 2.2). Earlier rounds are kept in git history only, not as separate files.

### 1.7 PR comments (issue #9)
- Stage PRs into the feature branch: no review comment. Findings and decisions are in `reviews/` and the session.
- The CI verifier posts one comment **only** when it fails, listing only the failing items (missing or stale report, open finding, unmatched SR finding) with ID, SR, file:line, one-line evidence, decision needed. When the next run passes, that comment is deleted. Full results go to the job log and job summary. Untrusted text in comments (evidence, file names) is rendered inert: inside a fenced code block with backticks replaced, `@` replaced by `@\u200b` (no mentions), no links or images, each item truncated to 200 characters.
- appsec-baseline `security-review.yml` (dormant): posts a comment only when its decision is `block` or `escalate`, listing only the findings that cause it (no artifact text). On `allow` it deletes an earlier comment. The full artifact stays in the job summary and the uploaded artifact.

### 1.8 Release until change 0002
`deploy.yml`: `build → dast (ZAP baseline) → deploy`. The `security-tester` job is removed. ZAP alerts don't stop the deploy; recorded as exception `EXC-001` (2.4), expiry **2026-12-31**.

Scripts treat every path from a report or a diff as data: before opening, `files` keys are resolved against the repo root and rejected if outside it or a symlink; subprocesses use argument lists of fixed executables (`git`, `gh`), never a shell string; YAML is read with `yaml.safe_load`; JSON with the standard parser and the schema.

The session runs the scripts from a checkout of appsec-baseline at the lock SHA (`.appsec-baseline/`, git-ignored), never from dogs-app.

### 2.2 Review report (`schemas/review-report.schema.json`, JSON Schema 2020-12, `additionalProperties: false`)

| Field | Type | Rule |
|---|---|---|
| `reviewer` | string | one of the reviewers `stages.yml` lists for that stage |
| `stage`, `change` | string | `intent\|spec\|plan\|code`; `^[0-9]{4}$` |
| `model` | string | full model ID (2.3) |
| `round` | integer | 1–3 |
| `appsec_sha` | string | `^[0-9a-f]{40}$`, must equal `appsec-baseline.lock` |
| `files` | object | path → SHA-256 hex of file contents for every file the reviewer reviewed |
| `verdict` | string | `allow` |
| `produced` | object | path → SHA-256 of a file written from this reviewer's output (`TRACE-`/`THREAT-`); empty for other reviewers |
| `findings` | array | findings schema (extended: `needs_human` boolean; `status`: `fixed\|open\|needs-human\|accepted-risk\|carried`; `exception` id when `accepted-risk`) |

Input limits (all strings valid UTF-8, no control characters except `\n` in `evidence`/`recommendation`):

| Field | Limit |
|---|---|
| `model` | `^claude-[a-z0-9-]{3,60}$` |
| `files` keys | ≤ 300 chars, `^[A-Za-z0-9._/-]+$`, repo-relative, no `..` segment, not absolute; ≤ 500 entries |
| `files` values | `^[0-9a-f]{64}$` |
| `findings` | ≤ 200 items; `id` `^[A-Z]+-[0-9]{3}$`; `file` as `files` keys; `line` integer 1–1 000 000 or null; `evidence` ≤ 2 000 chars; `recommendation` ≤ 2 000 chars |
| whole file | ≤ 256 KiB |

`status` is set by `gate.py`, never by the reviewer. In a committed report: any finding with an `SR-xxx` `sr_ref` must be `accepted-risk` with an `exception` id that is present and unexpired in `sr-exceptions.yml` at the lock SHA; `open`, `needs-human` and `fixed` are not allowed (fixed findings are dropped from the final report); `carried` is allowed only for non-SR findings.

Two formats: a reviewer **returns** its output in the findings schema (`schemas/findings.schema.json`: `reviewer`, `artifact` with the TRACE/THREAT markdown where applicable, `findings`); `validate.py` checks it, `write_artifact.py` writes `artifact` to the file, and the session then **commits** the review report above, which records the produced file's hash in `produced` but not the artifact text.

### 2.5 CI verifier (appsec-baseline `verify.yml`, called from dogs-app `security.yml` job `verify` as `uses: ai-sdlc-lab/appsec-baseline/.github/workflows/verify.yml@<lock SHA>`)
The `uses:` ref and the scanners job's appsec-baseline checkout use the same 40-hex SHA as `appsec-baseline.lock` (test `test_workflow_pins_match_lock`). Every action in `verify.yml` is pinned by commit SHA from the BL-01 allowlist; script dependencies (`jsonschema`, `PyYAML`) install with `pip --require-hashes` from a hashed lockfile.
Runs on every PR (`pull_request`, never `pull_request_target`), `permissions: {}` at workflow level; job `contents: read`, `pull-requests: write` (comments only); `persist-credentials: false`; `timeout-minutes: 15`; untrusted values only via `env`. Steps, all fail-closed:
1. Check out the PR head and the base branch separately. Read `stages.yml` and `appsec-baseline.lock` **from the base** (a PR that changes either is verified against the base version; the change itself needs the owner at the final PR).
2. Check the lock SHA is reachable from appsec-baseline `main` (GitHub compare API: status `identical` or `behind`); a fork-network commit fails.
3. Check out appsec-baseline at the lock SHA; run its scripts from there.
4. `classify.py`: changed paths from `git diff --name-status -M base...head`, both sides of renames, deletions included. **docs-only** iff every path matches `^docs/` and no entry is a symlink (mode 120000) or submodule (160000). Anything else = **code**.
5. For each stage folder touched: every reviewer in `stages.yml` has a report; schema-valid; `appsec_sha` = lock; every hash in `files` equals the PR head's file; the stage artifact's own hash is listed; no `open`/`needs-human` findings; every `accepted-risk` matches an unexpired exception.
6. `structure.py`: each `INT-/SPEC-/PLAN-/TRACE-/THREAT-` file has every heading of its template, each with non-empty content; first heading starts with the ID.
7. Plan stage: `crosscheck.py` reads every `SR-xxx` row with status covered in `TRACE-<NNNN>.md` and every `M-xx` mitigation in `THREAT-<NNNN>.md`; each must appear in the "Implements" column of at least one `PLAN-<NNNN>.md` step that names at least one test; it fails listing each ID without a step or test.
8. Code PRs: `named_tests.py` (every test named in this repo's `PLAN-` section exists in the test tree and passed in the JUnit report of the `tests` job, M-07) and `plan_drift.py` (every changed path of this PR is listed in this repo's `PLAN-` section; renames count both paths).

**`PLAN-<NNNN>.md` structure** (template `PLAN.md`): one `## Repo: <name>` section per repo (`dogs-app`, `lab-admin`, `appsec-baseline`). Each section has a steps table `| # | Files | Implements (spec § / SR / M-xx) | Tests |`; the Files column lists repo-relative paths or globs (`api/app/*.py`). A script picks the section whose `<name>` equals the repo it runs in (`GITHUB_REPOSITORY` name in CI, `git remote get-url origin` locally). One code PR per repo section.

### 2.6 Scanners (dogs-app `security.yml` job `scanners`, always runs)
- docs-only: gitleaks.
- code: Semgrep, OSV-Scanner, gitleaks, Trivy; + zizmor, actionlint when `.github/` changed; + Trivy config when `infra/` changed.
- Tools keep their pinned versions and SHA-256 checks.
- appsec-baseline PRs (scripts, lockfile, workflows): its `ci.yml` gains a `scanners` job running Semgrep, OSV-Scanner on the hashed lockfile, gitleaks, zizmor and actionlint, with the same pins; the job is a required check there.

### 2.7 Required checks on `main` (dogs-app)
After this change: `ci`, `security/verify / verify`, `security-gate`. `security-gate` needs `[verify, scanners]`, runs with `if: always()`, `permissions: {}`, `timeout-minutes: 5`, and fails unless every needed job's result is `success` (skipped or cancelled = fail). Removed: `security/requirements / review`, `security/threat-model / review`. Swapped in one lab-admin apply, run right before the owner merges this change's final PR.

## 5. Authorisation matrix

| Action | Owner | Main session | Author subagent | Reviewer subagents | CI |
|---|---|---|---|---|---|
| Start a change, answer questions, decide SR findings | yes | — | no | no | no |
| Write `INT/SPEC/PLAN`, code | — | yes | yes (hook: only the current stage's artifact file; at the code stage only files listed in this repo's `PLAN-` section; never `reviews/`) | no | no |
| Write `TRACE-/THREAT-` files | — | only via `write_artifact.py` from the validated reviewer JSON | no (hook) | no | no |
| Edit `.github/` | — | yes (code stage only) | no (hook) | no | no |
| Edit `.claude/`, `CLAUDE.md`, `REVIEW.md`, `stages.yml`, `appsec-baseline.lock`, `.appsec-baseline/` | yes | **ask**: owner approves each edit (static `permissions.ask` rules + hook, incl. Bash commands naming these paths) | no | no | no |
| Commit, push stage/feature branches, merge stage PRs | — | yes | no (no Bash) | no | no |
| Merge into `main` | **yes (only)** | no: owner instruction only; hook asks before any `gh pr merge` whose base is `main` (residual risk below) | no | no | no |
| `make apply`, `terraform apply` | yes | no (deny) | no | no | no |

Hook rule: `agent_id` present in the PreToolUse input = subagent; absent = main session. Default deny: for subagents the hook denies every write not allowed in this matrix; for the main session, permission rules `deny` `Bash(make apply*)`, `Bash(terraform apply*)`, `Bash(make destroy*)`, and `ask` for edits of `.claude/**`, `CLAUDE.md`, `REVIEW.md`, `stages.yml`, `appsec-baseline.lock`; the hook denies main-session edits of `.github/**` outside a `stage/<NNNN>-code` branch.

Residual risk (owner-accepted 2026-10-28): the session holds the owner's login and bypass. Command-pattern rules don't stop `gh api …/merge` or `git push origin HEAD:main`; the real control is the owner's trust plus issue #12 (parked).

## 7. Errors and logging
- Hook, gate, loop and verifier write **JSON Lines**, one event per line, with fields `ts` (RFC 3339 UTC, milliseconds), `level` (`INFO|WARN|ERROR`), `service` (`stage-loop|hook|gate|verifier`), `version` (appsec-baseline lock SHA), `event`, `outcome` (`success|failure|denied`), `reason` (machine code, e.g. `sr_finding`, `schema_invalid`, `path_outside_repo`), `actor` (`owner|session|<agent name>|ci`), `change` (`NNNN`), `stage`, `request_id` (session id or `GITHUB_RUN_ID`), plus event-specific fields. `source_ip`, `http` and `resource` don't apply (no HTTP requests).
- Events: `stage.start`, `stage.round`, `review.finding`, `gate.allow`, `gate.block`, `gate.escalate`, `owner.decision`, `authz.denied` (hook), `authz.ask` (hook), `input.rejected` (validate/verifier), `verify.pass`, `verify.fail`, `pr.merged`.
- Locally to `.claude/stage-log.jsonl`; in CI to stdout (job log) and a human summary to the job summary.
- Never logged: tokens, `Authorization` and `Cookie` headers, credentials, presigned URLs, request or response bodies, email addresses, names, full file contents, full reviewer output (only IDs, counts, paths, hashes).
- Errors (script exit ≠ 0, invalid reviewer JSON) stop the stage and are shown to the owner; never treated as allow.

## 11. Threat mitigations (from THREAT-0001)

Normative. How this section is produced: the security architect writes THREAT-<NNNN> during the spec stage; in the fix loop the author adopts every required mitigation here, keeping its M-ID, and the architect re-reviews. Each mitigation's tests are listed in §10.

| M-01 | The verifier computes changed files itself (`git diff -z --raw -M base...head`). A code PR (per `classify`) requires a code-stage report even when no stage folder changed; the security-code-reviewer report's `files` lists every changed non-docs file; the workflow-iac-reviewer report is required when `.github/` or `infra/` changed and lists those files. |
