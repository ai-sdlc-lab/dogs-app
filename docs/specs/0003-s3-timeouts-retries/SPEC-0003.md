# SPEC-0003: S3 calls get timeouts and bounded retries; S3 failure returns 503

<!-- Stage 2, derived from INT-0003.md. Behaviour and numbers, not implementation. Every limit is a number. -->

## 1. Behaviour

Applies to `GET /api/dogs` and `GET /api/dogs/{breed}`, the only endpoints that call S3 (listing objects; the presigned image URLs are signed locally and make no network call, but fall under the same deadline).

1.1 **Per-call limits.** Every S3 attempt waits at most 3 s to connect and at most 5 s for a response (read). Near the end of the overall deadline (1.3) these limits are shortened so that no attempt can run past it.

1.2 **Retries.** A failed S3 call is retried at most 2 times, so at most 3 attempts in total ("2 retries" = 3 attempts), using the standard retry mode of the S3 client, with backoff between attempts, and only if the call is idempotent. Listing is a read and qualifies. No write or other non-idempotent S3 call exists; none is retried.

1.3 **Overall deadline.** All S3 work of one request (every call, every attempt, every backoff wait) must finish within 8 s, counted from the first S3 call of the request. The deadline also bounds an attempt that is already running:
- an attempt that is still in progress at 8 s is abandoned, even if it keeps receiving data and never trips the read timeout (a "slow drip" response, for example one byte every 4 s);
- an attempt that starts shortly before 8 s gets only the time left, not the full 3 s plus 5 s;
- a backoff wait never runs past 8 s, and no attempt starts at or after 8 s.

Deadline and attempt state belong to one request only. They are never kept in the cached S3 client, a module global or any other state shared across threads or warm invocations: a slow first request does not shorten or fail a later or concurrent one.

An attempt abandoned at the deadline releases its resources: its connection is closed and no worker keeps running for it. A later request on the same warm client is served normally.

When 8 s is reached the request fails as in 1.4. The 503 is therefore sent at most about 8 s after the request's first S3 call, leaving a margin of at least 2 s under the 10 s function timeout.

1.4 **S3 failure.** The request fails as an S3 failure when, after the limits above, any of these happens: connect timeout, read timeout, connection error, an error response from S3 (any S3 error code or HTTP error status, including access denied), any other error raised by the S3 client library, or the overall deadline. Only these failures become `503`. The API then answers:
- status `503`;
- body exactly `{"error": "dependency_unavailable", "request_id": "<id>"}`, JSON, no other fields;
- `request_id` is the Lambda request ID of the invocation; if it is missing or empty, a freshly generated UUID (version 4, from a CSPRNG) is used. It is never empty and never copied from the caller's request (no request header, query or path value is used). It is a correlation ID for finding one invocation, not a token or secret;
- no exception text, path, bucket name, key, URL, host name or library name in the body;
- no `Retry-After` header;
- no fallback: no partial list, no cached data, no empty list. A failure part way through (for example the second listing page) fails the whole request.

1.5 **Unchanged behaviour.**
- A breed that does not match `^[a-z0-9-]{1,40}$` gives `404` without any S3 call, exactly as today. An `HTTPException` such as this `404` passes through and is never turned into `503`.
- With a healthy S3, `/api/dogs` and `/api/dogs/{breed}` return the same status and body as today, including `404` for a well-formed breed with no images.
- `/api/health` makes no S3 call and is unchanged, also while S3 fails.
- A failing S3 on `/api/dogs/{breed}` for a well-formed breed gives `503` (not `404`).
- A missing `DOGS_BUCKET` setting behaves exactly as today (not `503`).
- Any error that is not an S3 failure per 1.4 (for example a programming error) keeps today's response (`500`), not `503`.
- All other error responses are unchanged; see section 7.

1.6 **Headers.** The `503` carries the same SR-004 headers as every other response (`Content-Type: application/json; charset=utf-8`, `X-Content-Type-Options: nosniff`, `Strict-Transport-Security: max-age=31536000; includeSubDomains`, `Referrer-Policy: no-referrer`), set by the existing header layer.

## 3. Limits

| Limit | Value |
|---|---|
| S3 connect timeout | 3 s (maximum per attempt) |
| S3 read timeout | 5 s (maximum per attempt) |
| Retries per call | 2 (maximum; at most 3 attempts), standard retry mode, with backoff, idempotent calls only |
| Overall S3 deadline per request | 8 s (all calls, attempts and backoff; also bounds an in-flight attempt) |
| Function timeout (unchanged, infrastructure) | 10 s |
| Margin between deadline and function timeout | at least 2 s |

Without the overall deadline the per-attempt limits would allow up to about 24 s (3 attempts of 3 s + 5 s, plus backoff), and a slow-drip response could last longer still, which is why the 8 s deadline is part of this spec and applies to running attempts too.

## 7. Errors and logging

What the caller sees:

| Case | Status | Body |
|---|---|---|
| S3 failure (1.4) | `503` | `{"error": "dependency_unavailable", "request_id": "<id>"}` |
| Malformed or unknown breed | `404` | unchanged from today |
| Missing `DOGS_BUCKET`, other non-S3 error | as today (`500`) | unchanged from today |

Logging: this change adds none. A `503` therefore leaves no log record.

Accepted risk for this change (AUD-003, ARC-004): S3 outages are not logged. The detection route is an operator alarm on Lambda errors and duration (a hung S3 shows as long durations up to about 8 s; a `503` is a normal response and is not a Lambda error, so duration is the main signal). This risk is recorded in `decisions.md` as the agent's decision at the spec stage (AUD-001). Setting up that alarm is infrastructure, outside this change. A follow-up change that logs S3 failures as an SR-024 event is suggested (open question for the owner). Gaps D-1 of change 0002 (SR-005 bodies for 4xx/500, `error.unhandled`) stay open.

## 9. Acceptance tests (named)

All tests run without network. Timeout, retry and hang tests use the real S3 client library, configured as in production, over a stubbed transport (no hand-written replacement of the client, no mock of the retry logic), so the configured timeouts, standard retry mode and attempt count are the ones really exercised. Time-based tests use a controllable clock or short stub delays so the suite stays fast. Other tests may stub the S3 client where the API obtains it.
