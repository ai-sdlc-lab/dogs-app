# SPEC-0003: S3 timeouts, bounded retries and 503 on S3 failure (SR-006)

<!-- Stage 2, derived from INT-0003.md. Behaviour and numbers, not implementation. Every limit is a number. -->

## 1. Behaviour

### 1.1 Which calls
- "S3 call" means every network request the app makes to S3. Today that is only the listing (`ListObjectsV2`, one call per result page) made by `GET /api/dogs` and `GET /api/dogs/{breed}`. Presigning image URLs is local signing, makes no network request, and is not an S3 call.
- All S3 calls are reads (idempotent). The app issues no write, delete or other non-idempotent S3 call, and none is retried if one is ever added (INT-0003 out of scope).
- `GET /api/health` and the static web files make no S3 call and are unchanged.

### 1.2 Timeouts (per attempt)
- Connect timeout: **2 s**. Read timeout: **3 s**. Both are set explicitly on the S3 client, below the SR-006 maxima (3 s, 5 s).
- The SDK's own retries are off. Effective behaviour: exactly one HTTP attempt per SDK call (effective total attempts 1; botocore `total_max_attempts` 1, not merely a retry count of 1), so the retry rules of 1.3 are the only retries and the totals below cannot multiply.
- The S3 client is shared across requests and its timeouts are fixed (2 s / 3 s). The per-attempt cap to the remaining time (1.4) is enforced by the deadline wait, not by changing the client configuration per request.
- Unchanged: the client signs with `s3v4`, uses virtual-hosted addressing and the regional endpoint `https://s3.<region>.amazonaws.com` (existing test `test_presigned_urls_use_regional_endpoint`); TLS certificate validation stays on.

### 1.3 Retries and backoff
- A failed S3 call is retried at most **2 times** (3 attempts in total per call).
- Only transient failures are retried: connect timeout, read timeout, connection error, S3 HTTP `5xx`, and S3 throttling (`SlowDown`, `RequestTimeout`). Any other S3 error (for example `AccessDenied`, `NoSuchBucket`, other `4xx`) is not retried and goes straight to the `503` of 1.5.
- Backoff before retry *n* (n = 1, 2): computed delay = min(1 s, 0.2 s × 2^(n-1)), that is 0.2 s then 0.4 s (the 1 s cap applies to any further doubling: 0.8 s, then 1 s). The actual wait is drawn uniformly at random between 0 and the computed delay (full jitter).
- Jitter is load spreading, not a security value; it needs no cryptographic randomness.

### 1.4 Overall deadline
- All S3 work of one request (every call, every attempt, every backoff wait) has an overall deadline of **8 s**, measured with a monotonic clock from the moment the app starts handling the request. The Lambda function timeout stays **10 s**, so the `503` is sent at least 1 s before the platform would cut the invocation (2 s of margin remain for response handling).
- One monotonic deadline (8 s from the start of request handling) covers all result pages of a listing, all attempts and all backoff waits together; it is never restarted per page or per attempt. Each attempt may use at most the remaining time: the app stops waiting for it when the deadline is reached (1.2).
- A retry is **not started** if the remaining time is less than its computed backoff delay (1.3, not the jittered draw, so the rule is deterministic) plus **1 s**. The request then ends with the `503` at once, without waiting.
- If the deadline is reached while a call has not returned (a hanging S3), the app stops waiting and answers `503` at 8 s. The abandoned worker starts no new attempt and no backoff wait after the deadline; its late result or exception is dropped silently (no log line, no change to the response or any shared state) and has no effect on later requests; its own timeouts (2 s connect, 3 s read) still bound the call in flight.
- Lambda initialisation (cold start) is outside the request deadline; the 2 s margin and the 128 MB / 10 s settings in `infra/main.tf` are unchanged.

### 1.5 Response on S3 failure
- Only an error raised by the S3 list call, or the deadline, gives `503`. When an S3 call still fails after 1.3 and 1.4 (timeout, connection error, S3 error, deadline), the endpoint answers **`503`** with the fixed SR-005 body `{"error": "dependency_unavailable", "request_id": "<id>"}`, `Content-Type: application/json; charset=utf-8`. Never `500`.
- `<id>` is the platform request ID (Lambda request ID); when none exists (local or container run) a generated UUID.
- The body contains no AWS error text, exception message, stack trace, host name, bucket name, key or URL.
- The `503` carries these SR-004 headers, each exactly once: `X-Content-Type-Options: nosniff`; `Strict-Transport-Security: max-age=31536000; includeSubDomains`; `Referrer-Policy: no-referrer`; `Content-Type: application/json; charset=utf-8`. No CSP/COOP (not HTML), no `Access-Control-*`, no `Cache-Control`. They are applied by the single app-wide header wrapper (SPEC-0002 1.2); the `503` is produced inside the app and passes through it like any response, with no second code path that builds a 503.
- All-or-nothing: if any page of a listing fails, the whole request answers `503`; no partial list is returned.
- Fail closed: a failure never falls back to behaviour that skips a check (there is no cache, no stale data, no unsigned URL, no default list).
- Failures that are not S3 list-call failures (a bug in the app, a presigning error, any other exception) are unchanged: `500` through the last-resort handler (existing `test_security_headers_on_unhandled_error`). The owner can tell `503` (dependency) from `500` (bug).

### 1.6 Log event
- One log line per failed request (not per attempt), JSON Lines on stdout, one event, values JSON-encoded. Event name `dependency.unavailable` is a **new** `<area>.<action>` event, not in the SR-024 baseline vocabulary (EXC-002 covers that absence; the baseline is not edited here).

| Field | Value |
|---|---|
| `ts` | RFC 3339 UTC with milliseconds |
| `level` | `ERROR` |
| `event` | `dependency.unavailable` |
| `outcome` | `failure` |
| `request_id` | the same value as in the response body |
| `actor` | `anonymous` (the app has no identities) |
| `source_ip` | only from the platform request context (function URL `requestContext.http.sourceIp`), never from any header (`X-Forwarded-For` or other); `unknown` when the platform gives none (local or container run) |
| `http` | `{"method": "<method>", "path": "<path>", "status": 503}`: the path has no query string and is truncated to 256 characters |
| `resource` | `{"type": "dependency", "id": "s3"}` |
| `reason` | `dependency_unavailable` |
| `cause` | fixed allow-list, one of `timeout`, `connection`, `throttled`, `server_error`, `denied`; never AWS text (deadline and connect/read timeouts give `timeout`; connection error `connection`; `SlowDown`/`RequestTimeout` `throttled`; S3 `5xx` `server_error`; `AccessDenied`, `NoSuchBucket` and other `4xx` `denied`) |
| `service` | `dogs-app` |
| `version` | the full git commit SHA of the build. `make build` writes it into a version file inside the Lambda zip; the app reads that file once at start. If the file is absent or its content does not match `^[0-9a-f]{40}$`, `version` is `unknown`. No infrastructure, IAM or CI change (IAC and CI not triggered); only the zip contents change |

- Values are JSON-encoded, so control characters in the path (for example newline) cannot forge or split a log line.
- Never in the log: AWS error text, exception messages, stack traces, presigned URLs, query strings, headers, bodies.

### 1.7 Resources
- Anything opened for S3 access (response bodies and streams, temporary objects, connections the app holds) is released on success, on failure and on the deadline path, using context managers or `finally`.
- A failed or abandoned call leaves no state that changes a later request: the next request starts with a fresh deadline and fresh attempts.

### 1.8 What does not change
- Routes, success responses, `404` `{"detail": "unknown breed"}` bodies and the breed validation (`^[a-z0-9-]{1,40}$`, checked before any S3 call) are unchanged. The frontend is unchanged (it shows no specific `503` message).
- No new AWS service, IAM change, dependency or infrastructure change; the Lambda timeout stays 10 s.

## Decisions made by the author

- **D-1 (non-transient S3 errors):** `AccessDenied`, `NoSuchBucket` and other `4xx` get `503` without retry (retrying cannot help); INT-0003 says only that a failing S3 returns `503`.
- **D-2 (retry rule uses the computed delay):** the "remaining time < delay + 1 s" check uses the un-jittered computed delay, so it is deterministic and testable.
- **D-3 (SDK retries off):** the SDK's own retries are disabled so the app's rule (at most 2 retries, 8 s) is the only retry, avoiding hidden multiplication.
- **D-4 (log values the baseline leaves open):** `resource` is `{"type": "dependency", "id": "s3"}` (no bucket name), `service` is `dogs-app`, `source_ip` and `version` fall back to `unknown`.
- **D-5 (no Retry-After, no Cache-Control):** not required by SR-004/005/006 and not asked by INT-0003.
- **D-6 (version is the commit SHA):** SR-024 needs `version` to be the git commit SHA. `make build` writes the full SHA into a version file inside the Lambda zip; the app reads it once at start and logs it; absent or not matching `^[0-9a-f]{40}$` gives `unknown`. Needs no infrastructure, IAM or CI change (only the zip contents change).
