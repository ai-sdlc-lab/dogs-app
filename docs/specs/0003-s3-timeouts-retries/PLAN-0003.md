## Order of work

Work in step order. Each step writes its tests in the same commit as the code, and the tests come first (they fail before, pass after).

1. **A-01 (client config):** explicit timeouts and one SDK attempt. Everything else builds on a client that cannot multiply attempts.
2. **A-02 (retry loop, deadline, worker):** the core. A-03 to A-06 depend on it.
3. **A-03 (503 handler):** the exception raised by A-02 becomes the 503, through the existing header wrapper.
4. **A-05 (version file, EXC-003):** the reader and the `VERSION` constant, before the log event that uses it.
5. **A-04 (log event):** needs the handler of A-03 and `VERSION` of A-05. Then **A-06 (`make build`):** the build step that writes the file.
6. **A-07 (SR-007 / SR-013 / SR-023 evidence):** tests only, no code change.
7. **A-08 (docs):** last, once the behaviour is real.

**Not in this plan (documented gaps, owner decides at the merge to `main`):** SR-005 other error bodies and `error.unhandled` (SPEC-0002 D-1), SR-022 S3 TLS-version deny (SPEC-0002 D-3), other mandatory SR-024 events (decision 6). No step changes the frontend, the Lambda timeout, IAM, infrastructure or CI.

Each call goes through `attempt(fn)`: up to 3 attempts; a retry only for `ConnectTimeoutError`, `ReadTimeoutError`, `EndpointConnectionError`, `ConnectionError`-class botocore errors, `ClientError` with HTTP status >= 500 or code `SlowDown` / `RequestTimeout`; any other `ClientError` (`AccessDenied`, `NoSuchBucket`, other 4xx) maps to a cause and raises at once. Botocore exceptions that are not `ClientError` and not connection/timeout errors (`NoCredentialsError`, `ParamValidationError`, any other `BotoCoreError`) are a bug or configuration fault (AC-7): they are not retried, are not mapped to `DependencyUnavailable`, and propagate unchanged (re-raised in the request thread from the worker) to the last-resort `500`; only the connection/timeout classes above are retried and end as `503`. Backoff: `delay(n) = min(1.0, 0.2 * 2**(n-1))`, wait `random.uniform(0, delay(n))` through a module-level `sleep`; before a retry, if `deadline - clock() < delay(n) + 1.0` (the computed delay, not the draw) no retry starts and the failure is raised at once. `clock` (`time.monotonic`) and `sleep` are module-level names, so tests replace them with a controllable clock. **Deadline:** one `Deadline(start + 8.0)` created at the start of request handling (first line of the route, before any S3 work) and shared by all pages, attempts and backoffs. The request thread starts a fresh daemon `threading.Thread` per request (not a shared pool, so a hung worker can never block a later request), waits on a `threading.Event` / `queue` with `timeout = remaining`, and on timeout raises `DependencyUnavailable("timeout")` at 8 s. A per-request `cancelled` flag is set by the request thread when it stops waiting; the worker checks it before every attempt and before every backoff wait, and when it is set returns without a call, without a wait, without a log line and without touching the response or any shared state; a late result or exception is dropped (M-01). The worker holds no reference to the response. Any S3 response body or stream used is closed in `finally` / a context manager on success, on failure and on the deadline path (M-08). Non-transient errors are not retried (M-06). Any page that fails fails the whole request: no partial list, no cache, no stale or default fallback (M-07). ## Test plan

- **Where the tests run:** all new tests live in the new file `api/tests/test_s3_failure.py` and run with `make test-api` (`cd api && pytest`), so also in `make test`, in `ci.yml` job `api` and in `security.yml` job `tests` (both unchanged). `test_architecture_mentions_s3_deadline` (A-08) sits in the same file and reads `../docs/architecture.md`.
- **No real waiting:** `main.clock` and `main.sleep` are replaced by a fake clock (a list-backed counter; the fake `sleep(x)` and the stubs advance it). `test_s3_deadline_with_hanging_stub` has two parts: the fake-clock part asserts the 503 and the app-clock time of 8 s; the real-clock part runs the hanging stub and asserts the client has the response in under 9 s (real wait, the only slow test, about 8 s), then releases the stub and requests again to show the abandoned call does not break the next request. The abandoned worker of `test_abandoned_worker_makes_no_further_attempts` is released after the deadline with a transient error and the test asserts no further stub call, no fake `sleep` call, no stdout line and an unchanged response.
- **Parametrisation:** `test_non_s3_error_still_500` runs over a presign error, a generic `RuntimeError`, and the list-call errors `NoCredentialsError`, `ParamValidationError` and a plain `BotoCoreError` (each: status 500, one call only, no retry, no `dependency.unavailable` line). `test_s3_failure_returns_503` runs over the five failing-stub errors (`ConnectTimeoutError`, `ReadTimeoutError`, `EndpointConnectionError`, `ClientError` 500, `ClientError` `SlowDown`) and over `GET /api/dogs` and `GET /api/dogs/pug`. `test_dependency_unavailable_log_event` checks the right `cause` per error, the `/api/dogs?x=1` path without query, a newline in the path (one line), a path over 256 characters (cut to 256), `source_ip` from the context (a request made with a Mangum-style scope carrying `aws.event` and `aws.context`) and not from `X-Forwarded-For`.
- **Version tests:** `test_version_unknown_when_missing_or_invalid` is parametrised over: absent, empty, upper case, 7, 39, 41 characters, `../x`, content with an embedded newline in the middle, non-ASCII bytes. `test_version_file_read_is_capped_and_never_raises` uses a 1 MB file (the read stops at 64 bytes and the result is `unknown`), a directory in place of the file, and a file with no read permission (skipped when the process is root).
- **Real botocore, no network:** A-01 uses a `before-send` handler on the real client so the test counts requests that would have been sent; no network call is made.
- **Unchanged tests that must still pass:** `test_health`, `test_lists_only_well_formed_keys`, `test_by_breed`, `test_unknown_or_invalid_breed_is_404`, `test_presigned_urls_use_regional_endpoint`, `test_no_api_docs_exposed`, `test_security_headers_on_unhandled_error` and the other `test_headers.py` tests. Their `FakeS3` stubs get a `list_objects_v2` method (A-02); their assertions do not change.
- **Lint:** `make lint` (`ruff check` and `ruff format --check` on `api/`).
- **Release evidence (not unit tests):** after the owner's merge, the built zip contains `app/BUILD_SHA` with the commit SHA (check with `unzip -p build/lambda.zip app/BUILD_SHA`, locally before the merge).

## Rollout and rollback

- **Rollout:** the code PR merges into `feature/0003-s3-timeouts-retries` once `make test` and `make lint` pass. The owner's merge of the feature branch to `main` starts `deploy.yml` (build with the version file, ZAP, deploy, smoke test). Nothing else is migrated.
- **Failure before deploy:** nothing is deployed and the running version stays.
- **Failure after deploy:** if S3 is slow or down the endpoints answer `503` within 8 s instead of failing at the platform's 10 s; the frontend is unchanged and shows its existing error text. If `BUILD_SHA` is missing, logs show `version` `unknown` and nothing else changes.
- **Rollback:** the owner reverts the merge commit on `main` (a PR, owner-approved) and `deploy.yml` deploys the previous build. Agents never merge to `main` or run `make apply`. No data or infrastructure migration is involved.
- **After release:** the manual check (optional) is that `GET /api/dogs` still returns 200 with images; an S3 outage cannot be provoked on purpose in production.
