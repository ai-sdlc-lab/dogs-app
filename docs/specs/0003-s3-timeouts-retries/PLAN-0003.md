### Settled design points (left open by the spec)

**Today's missing-`DOGS_BUCKET` behaviour (pinned from the current code).** `list_dogs` does `os.environ["DOGS_BUCKET"]`. A missing setting raises `KeyError` in the sync endpoint. No handler catches it, so Starlette's `ServerErrorMiddleware` answers status `500`, body `Internal Server Error` (plain text), and with the test client's default `raise_server_exceptions=True` the exception is re-raised to the caller. `test_missing_bucket_setting_unchanged` therefore uses `TestClient(..., raise_server_exceptions=False)` and asserts `500` with that body, and the `KeyError` is read before the S3 error scope is entered so it can never be classified as S3 failure (it is also not a botocore exception).

**Clock.** One module function `now()` in `s3_limits.py` (wraps `time.monotonic`) is the only time source of the deadline code. Tests replace it with a fake clock. The stub transport advances the fake clock instead of sleeping, and `time.sleep` is monkeypatched in these tests to advance the same fake clock (botocore's backoff calls `time.sleep`). The suite stays fast and exact. The concurrent half of `test_deadline_is_per_request` cannot share one fake clock, so it uses real time with the deadline constant monkeypatched down to 0.4 s and stub delays of at most 0.05 s per step.

**Where per-request state lives (M-09).** A `contextvars.ContextVar` holds the request's `Deadline` object (start time and 8 s limit). `list_dogs` opens a `s3_deadline()` scope (set on entry, reset in `finally`) at its first S3 call. The sync endpoint runs in its own worker thread with a copied context, so concurrent requests and later warm invocations each see their own value. The cached client, module globals and the session hold no deadline or attempt state.

**How a running synchronous boto3 attempt is bounded (M-01, M-02, M-10).** No thread, no new dependency. The client's HTTP layer is replaced by `DeadlineSession`, a subclass of botocore's own `URLLib3Session` (botocore is already a dependency):
- Per attempt: `send()` reads the request's `Deadline`. If no time is left it raises `DeadlineExceeded` before touching the network (no attempt starts at or after 8 s). Otherwise it sends through a shallow per-call copy of the session (shares the connection pool, own timeout values) with connect timeout `min(3, left)` and read timeout `min(5, left)`. Nothing shared is mutated.
- Slow drip: the response body wrapper reads in small chunks. Before every chunk it sets the socket timeout of the connection to `min(5, left)` and checks the deadline; at 8 s it closes the connection (releases it, not back to the pool) and raises `DeadlineExceeded`. One blocked read is therefore also limited to the time left, so no attempt can end later than the deadline plus scheduling noise.
- Release: on deadline, on any error and on normal end, the connection is closed or returned in a `finally`; no thread is started, so none can linger.
- `DeadlineExceeded` is not a retryable botocore error type, so the standard retry handler does not retry it; it propagates out of the call.
- Backoff: a `needs-retry` hook registered first on the client's event system (same module, reads the context variable) raises `DeadlineExceeded` when a retry would be due and the time left is not more than the largest possible backoff for that attempt (1 s after attempt 1, 2 s after attempt 2, from the standard mode formula). No sleep then starts and no attempt follows, so a backoff never runs past 8 s. When more time is left the standard mode runs unchanged.
- Primary approach (decided here): the `DeadlineSession` subclass plus the `needs-retry` hook above. The supported hook is used where one exists (`needs-retry` event, `Config` timeouts and retries). Private parts used: `URLLib3Session.send`, `AWSResponse.raw` and the client's `_endpoint.http_session` attribute (to swap the session in `install(client)`).
- Pinned version: `api/requirements.txt` already pins `botocore==1.43.117` (with `boto3==1.43.114`, hashes, from `api/requirements.in`). The pin is exact, so no requirements change is needed; the private parts above are verified against exactly this version. `test_botocore_internals_available` fails loudly (naming the missing item) if any of them is absent, e.g. after a version bump. Only if a part is unusable may the approach change (e.g. a deadline watchdog timer always cancelled in `finally`), with `PLAN-0003.md` updated in the same PR and the named tests unchanged.

**Classification (M-03).** `list_dogs` runs the S3 work inside `try`; `botocore.exceptions.BotoCoreError`, `botocore.exceptions.ClientError` and `DeadlineExceeded` become `S3Unavailable`. Nothing else is caught. `HTTPException` (raised outside `list_dogs`, or passing through) and programming errors are not touched. `S3Unavailable` has a FastAPI exception handler that returns `JSONResponse(status_code=503, content={"error": "dependency_unavailable", "request_id": rid})`, no headers added; the existing outer header layer sets the SR-004 headers and `charset=utf-8`.

**request_id (M-05, SR-021).** Taken from `request.scope["aws.context"].aws_request_id` (set by Mangum); if missing or empty, `str(uuid.uuid4())` (CSPRNG). No request header, query or path value is read. The handler does not log.

## Test plan

All tests run offline, with no AWS credentials needed (fake keys set by the fixture).

- Timeout, retry, hang, slow-drip, deadline and release tests use the real botocore client built by the production `s3()` function, with the production `Config` and the production `DeadlineSession`. Only the bottom of the session (the call that opens the connection and the raw response object) is replaced by the stub in `s3_stub.py`. The retry logic, the configured timeouts and the attempt count are the real ones. No hand-written replacement of the client and no mock of the retry code.
- Time: a fake clock (`now()` replaced; stub and `time.sleep` advance it). `test_s3_hang_returns_503_before_function_timeout` asserts the fake-clock time from request start is under 10 s (in practice at most 8 s). `test_s3_slow_drip_returns_503_before_function_timeout` uses a raw body that yields one byte per 4 fake seconds. `test_attempt_started_near_deadline_is_bounded` makes attempts 1 and 2 fail at fake 2.9 s and 7.0 s and asserts that the third attempt (if started) is given at most the time left as connect and read timeout. `test_backoff_does_not_exceed_deadline` forces the fake clock so a backoff would cross 8 s and asserts the sleep is never entered and no further attempt reaches the stub. `test_no_retry_after_deadline` asserts the stub is not called once 8 s are used.
- `test_at_most_three_attempts`: stub always fails; counts calls per paginator call, expects 3.
- `test_deadline_is_per_request`: sequential half on the fake clock (first request hangs to 503, second healthy request returns 200 on the same cached client); concurrent half with two threads in real time and a shortened deadline (see Clock above): one hangs to 503, the other healthy returns 200 and is unaffected.
- `test_abandoned_attempt_releases_resources`: after a deadline 503 the stub's raw body object reports closed and not returned to the pool, `threading.active_count()` equals its value before the request, and a following healthy request on the same client returns 200.
- API-level tests use `TestClient(..., raise_server_exceptions=False)` and a small wrapper ASGI app that sets `scope["aws.context"]` (as Mangum does) for the Lambda request ID tests. `test_503_ignores_request_id_header` sends `X-Request-Id` and `request_id` headers and a query value. `test_s3_failure_body_has_no_detail` makes the stub raise errors whose text carries a marker string, a path and the bucket name, and asserts none appears in the body or any header.
- `test_s3_connection_error_returns_503` is parametrised over connect timeout, read timeout and connection error. `test_s3_error_response_returns_503` uses a stub S3 error response (`AccessDenied`, 403). `test_s3_other_client_error_returns_503` raises a generic `BotoCoreError` subclass.
- `test_s3_failure_adds_no_log_record`: with the stub failing, `caplog` (all loggers, level DEBUG) holds no record from the app's loggers (`app.*` and the root logger's own records) created by the 503 path; botocore and urllib3 loggers are excluded from the assertion; the test documents the accepted risk and is replaced when the logging follow-up is done.
- `test_non_s3_error_not_503`: the stub raises `ValueError`; the response is `500` (not `503`). `test_missing_bucket_setting_unchanged`: `500`, body `Internal Server Error` (pinned above), not `503`.
- Mapping check: every M-01 to M-10 and every covered SR of TRACE-0003 (SR-001 to SR-007, SR-021, SR-022) appears in a row above with named tests; M-08 is the accepted logging risk, pinned by `test_s3_failure_adds_no_log_record` (T-12).
- Real socket: `test_slow_drip_abandon_over_real_socket` runs a loopback `socketserver` thread that sends headers then one byte at a time; the deadline constant is monkeypatched to about 1 s; asserts a 503 within the shortened deadline plus slack, the server sees the connection closed, and a following healthy request on the same client succeeds.
- Gate: `make test` passes locally; `make lint` (ruff clean) runs in CI.

## Infrastructure and IAM changes

None. No Terraform, IAM, workflow, dependency or AWS service change. The function timeout stays 10 s; only code under `api/app/`, tests under `api/tests/` and `docs/architecture.md` change. Because botocore is already a dependency and bundled in the Lambda zip, `make build` needs no change.

## Rollout and rollback

Rollout: normal CI deploy on `main` after the owner approves the final PR. The change takes effect on the first cold start. After deploy, the owner checks `GET /api/health` (200) and `GET /api/dogs` (200 with images) once.

Rollback: revert the merge commit and let CI redeploy; there is no data, schema or infra to undo. Residual items for the owner (open from the spec): failure logging follow-up, and the operator alarm on Lambda duration (M-08, outside this change).
