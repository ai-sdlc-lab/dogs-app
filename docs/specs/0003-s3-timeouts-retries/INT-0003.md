# INT-0003: S3 timeouts, bounded retries and 503 on S3 failure

Source: GitHub issue #31 (fix a gap against SR-006, "Dependency failures and timeouts").

## Problem
The existing gallery code calls S3 without explicit limits. The S3 client has no connect timeout (SR-006 requires at most 3 s), no read timeout (at most 5 s) and no bounded retries (at most 2, with backoff, idempotent calls only). When S3 is slow or down, a request can hang until the Lambda function timeout (10 s, per `infra/main.tf`), and a failed S3 call returns `500` instead of `503` with the SR-005 error body. There is no test that simulates a failing S3. Needed now because SR-006 is a MUST and the code does not meet it.

## Users and actors
- Gallery visitors (all users): get a fast, clear `503` instead of a hang or a misleading `500` when S3 is unavailable.
- The owner/operator: can tell a dependency outage (`503`) from an application bug (`500`) in responses and logs.
- S3 (dependency): called by the API for listing and reading images.

## What changes
### Functional
- Every S3 call has a connect timeout of at most 2 s and a read timeout of at most 3 s (lower than the SR-006 maxima of 3 s and 5 s, so the budget below holds).
- Failed S3 calls are retried at most 2 times (3 attempts in total), and only for idempotent (read) calls.
- Backoff between attempts is exponential with jitter: base delay 0.2 s, doubling per retry, each delay at most 1 s, with random jitter (delay drawn between 0 and the computed value).
- Time budget: the Lambda function timeout is 10 s (unchanged). All S3 work for one request, including attempts and backoff, has an overall deadline of 8 s from the start of the request. A retry is not started if the remaining time is less than its backoff delay plus 1 s. When the deadline is reached or retries are skipped, the API answers `503` immediately, so the response is sent at least 1 s before the function timeout.
- When S3 still fails (timeout, connection error, S3 error) the API answers `503` with the SR-005 error body, not `500`.
- The `503` response carries the same SR-004 security headers as every other response.
- An S3 failure logs one event in the SR-024 JSON Lines format with `event=dependency.unavailable`, `level=ERROR`, `outcome=failure`, `reason=dependency_unavailable` and the `request_id`, plus the other mandatory SR-024 fields (`ts`, `actor`, `source_ip`, `http` with method, path without query string and status `503`, `resource`, `service`, `version`). The log and the response contain no AWS error text and no presigned URLs.
- A failure never falls back to behaviour that skips a security check.
- Any resource opened for S3 access (streams, temporary objects) is released on success and on failure.
- A test with a failing S3 stub asserts the `503` response.

### Visual
None. Decision: no frontend change (the frontend does not show a specific message on `503`).

## Data handled
| Data | Source | Personal/sensitive? | Kept for |
|------|--------|---------------------|----------|
| Dog image objects and their keys/listing | S3 bucket | No | Not stored by the API; read per request |
| Error response body (SR-005 format) | API | No (must not leak S3 error details) | Not stored; logged per existing logging rules |
| Failure log event (outcome, reason code, request_id) | API | No (no AWS error text, no presigned URLs) | Per existing log retention |

## Trust assumptions
- S3 is trusted for content but not for availability: it may be slow, fail or time out.
- Callers (browsers) are untrusted; the `503` body must not expose internal or AWS error details.
- The AWS SDK's own default timeouts and retries are not trusted; limits are set explicitly.

## Out of scope
- Other SR requirements and other gaps in the existing code.
- New AWS services, caching, circuit breakers, or changes to the Lambda function timeout value (stays 10 s).
- Frontend changes.
- Retries of non-idempotent calls (the app is read-only, so none are expected).

## Success criteria
1. Every S3 call has a connect timeout of at most 2 s and a read timeout of at most 3 s (within the SR-006 maxima).
2. S3 calls are retried at most 2 times, only for idempotent calls, with exponential backoff with jitter: base 0.2 s, each delay at most 1 s.
3. Total time for one request, including all attempts and backoff, is at most 8 s (overall S3 deadline), against the 10 s Lambda function timeout; no retry starts when less than its backoff delay plus 1 s remains. A test with a stub that always hangs asserts the `503` is produced in at most 8 s.
4. With S3 failing (stubbed), the API returns status `503` with the SR-005 body, and never `500`.
5. The `503` response includes the same SR-004 security headers as a `200` response; a test asserts this.
6. An S3 failure logs an event `dependency.unavailable` at level `ERROR` with `outcome=failure`, `reason=dependency_unavailable` and `request_id`; a test asserts the log and the response body contain no AWS error text and no presigned URL.
7. A test using a failing S3 stub asserts the `503` status and body, and passes in `make test`.
8. Resources used for S3 access are released on both success and failure paths.
9. `make lint` and `make test` pass.
