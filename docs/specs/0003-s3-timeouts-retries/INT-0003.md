# INT-0003: S3 calls get timeouts and bounded retries; S3 failure returns 503

## Problem
GitHub issue #31 (finding AUD-003, severity high, debt carried over from change 0002, recorded as D-9 in `SPEC-0002.md`): requirement SR-006 (dependency failures and timeouts) is not met.

- The API's S3 client sets no explicit timeouts and no retry limit, so a slow or hung S3 can hold a request until the function's 10 s timeout kills it.
- When S3 fails, the API answers `500` (unexpected error) instead of `503` (dependency failure).
- No test makes S3 fail and checks the response.

Why now: it is an open high finding; the owner wants the debt closed.

## Users and actors
- Visitors of the dog gallery: they see a clear, quick "temporarily unavailable" answer instead of a hang or a misleading "server error" when S3 is down.
- The owner / operators: can tell a dependency outage (`503`) from a bug (`500`).
- S3 (the only outbound dependency of the API): its calls (listing images, creating presigned image URLs) are the ones affected.

## What changes
### Functional
Applies to both data endpoints (`/api/dogs` and `/api/dogs/{breed}`), per SR-006:
1. Every S3 call has a connect timeout of at most 3 s and a read timeout of at most 5 s.
2. Per-attempt limits alone are not enough: connect 3 s and read 5 s with 2 retries could reach about 24 s, over the 10 s function timeout. So one request has an overall deadline of 8 s for all its S3 work (every call, every attempt, backoff waits included). When the deadline is reached, the work stops and the request fails as an S3 failure (item 4). The 503 is therefore sent before the function timeout (10 s), leaving at least 2 s margin.
3. Retries are at most 2, with backoff, and only for idempotent calls (listing is a read, so it qualifies). Retries also stop when the overall deadline is reached.
4. When S3 fails (timeout, connection error, an S3 error response, or the overall deadline) after those limits, the API answers `503` with the SR-005 error body `{"error": "dependency_unavailable", "request_id": "<id>"}`. `request_id` is the Lambda request ID, or a generated UUID if the Lambda request ID is missing. No exception text, path, or library detail is in the body. There is no fallback that returns partial or cached data. The status code `503` is the only operator signal for now (logging is out of scope); a follow-up change for failure logging is suggested.
5. No `Retry-After` header is added to the `503`.
6. An unknown breed or a malformed breed still gives `404`; a healthy S3 behaves as today (same responses for success). `/api/health` is unchanged.
7. A test with a failing S3 stub asserts `503` and the exact body (SR-006 evidence).

### Visual
None. (The web app may show whatever it already shows for a failed API call; no new screen or text is requested.)

## Data handled
| Data | Source | Personal/sensitive? | Kept for |
|---|---|---|---|
| Dog image object keys (`dogs/<breed>/<file>`) and presigned image URLs | S3 bucket | No | Not stored; built per request |
| Error response (`error` code, `request_id`) | Generated by the API | No | Not stored by this change |

## Trust assumptions
- S3 is trusted for content but not for availability or latency: it may be slow, hang, or fail, and the API must bound that.
- Callers are untrusted; nothing from the request is copied into the error body.
- The function timeout (10 s, fixed in infrastructure) is trusted as the outer limit and is not changed.
- botocore/boto3 (already installed) is the S3 client; no new dependency or AWS service.

## Out of scope
- Anything else in SR-005 beyond the `503` body for S3 failure: the fixed error body for 4xx and `500` responses, and `error.unhandled` logging stay as they are (gap D-1 of change 0002).
- SR-024 log format and any new logging requirement (including logging S3 failures; suggested as a follow-up).
- A `Retry-After` header.
- SR-022 (TLS version), SR-007 (function timeout, concurrency), infrastructure changes.
- Other outbound calls (there are none today) and the frontend.

## Success criteria
1. The S3 client is configured with connect timeout <= 3 s and read timeout <= 5 s; a test reads the configured values.
2. The S3 client is configured for at most 2 retries; a test reads the configured value.
3. With a stubbed S3 that always fails, `GET /api/dogs` and `GET /api/dogs/{breed}` return status `503` with body exactly `{"error": "dependency_unavailable", "request_id": "<id>"}` (`request_id` non-empty: the Lambda request ID, or a UUID when it is missing), and the body contains no exception message, path or library name. A named test (set in the plan) asserts the exact body.
4. With a stubbed S3 that hangs, a test shows the request ends with `503` in under 10 s (the overall S3 deadline is 8 s), retries included.
5. With a healthy S3 stub, responses for `/api/dogs`, `/api/dogs/{breed}` (found and unknown, `404`) and `/api/health` are unchanged from today.
6. The 503 response carries the same SR-004 security headers as every other response.
7. `make test` and `make lint` pass.

## Decided (earlier open questions)
1. Error code: `dependency_unavailable`.
2. `request_id`: the Lambda request ID, or a generated UUID if missing.
3. No `Retry-After` header.
