# INT-0002: Security response headers on every response (SR-004)

## Problem
The app's responses do not carry the response headers that security requirement SR-004 requires (`docs/architecture.md`, "Known gaps": "current code predates SR-004 headers"). Without them, browsers may guess (sniff) content types, can connect over plain HTTP before switching to HTTPS, send the page URL as a referrer to the image host, and let the page be framed by other sites or load scripts, styles and images from origins the app never uses. The app is public and unauthenticated, so any visitor's browser is affected. This change closes the SR-004 gap for every response the app produces: the API and the web page at `/`.

## Users and actors
- **Visitors (anonymous, any browser):** receive the headers; their browser enforces them. No accounts exist.
- **API callers (any client on the internet):** receive the same common headers on `/api/*` responses.
- **S3 image host:** loads gallery images through presigned URLs; it must stay allowed as an image source on the HTML page.
- **Owner:** approves the merge to `main`, which deploys the change.

## What changes

### Functional
1. Every response the app produces carries these headers, with these exact values:
   - `X-Content-Type-Options: nosniff`
   - `Strict-Transport-Security: max-age=31536000; includeSubDomains`
   - `Referrer-Policy: no-referrer`
   - `Content-Type` that matches the body, with `charset=utf-8` for text types (for example HTML, JSON, CSS, JavaScript).
2. "Every response" covers: successful API responses (`/api/health`, `/api/dogs`, `/api/dogs/{breed}`), API error responses (4xx and 5xx, including validation errors and unhandled errors), 404s for unknown paths (under `/api/` and outside it), the HTML page at `/`, and static assets of the web build (scripts, stylesheets, images, icons).
3. HTML responses additionally carry:
   - `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' https://<image-host>; connect-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'; object-src 'none'`, where `<image-host>` is the regional S3 host the gallery's presigned image URLs point to. The policy contains no `unsafe-inline` and no `unsafe-eval`.
   - `Cross-Origin-Opener-Policy: same-origin`
4. Non-HTML responses (JSON, scripts, stylesheets, images) do not carry the CSP or COOP headers.
5. No CORS headers (`Access-Control-*`) are added to any response.
6. No `Cache-Control` header is added or changed by this change.
7. Existing response bodies, status codes and routes are unchanged.
8. The image host named in the CSP is always the same host the app's presigned image URLs point to, so the CSP allows exactly the images the gallery shows and no other host. Any infrastructure setting needed to give the app that host follows the repo rules: names `sdlc-lab-app-*`, tag `project=sdlc-lab`, region eu-north-1, no change to IAM permissions or S3 public-access settings, and no new AWS service.
9. The guarantee covers responses the app's code produces. Responses generated by the Lambda platform outside the app's code (for example a function timeout, a throttle, or a platform 5xx before the app runs) cannot carry these headers and are outside this guarantee.

### Visual
None. The gallery looks and behaves as today: the page loads, the breed filter works, and images from S3 display. (The current page uses no inline scripts or styles, so the CSP is expected not to block anything the page needs; success criterion 7 checks this.)

## Data handled
| Data | Source | Personal/sensitive? | Kept for |
|---|---|---|---|
| Response header values (fixed strings from SR-004) | App configuration/code | No | Not stored; sent with each response |
| S3 regional image host name (used in the CSP `img-src`) | Deployment (bucket name and region eu-north-1) | No (public hostname, already visible in presigned URLs) | Not stored beyond the app's deployed configuration |

No new data is collected, stored or logged. No personal data is involved.

## Trust assumptions
- All callers are untrusted and anonymous (trust boundary 1 in `docs/architecture.md`); the headers are fixed values and never depend on request input (headers, query, path).
- Browsers are trusted to enforce the headers; the headers are defence in depth, not a replacement for server-side checks.
- The S3 regional host is trusted as an image source only (`img-src`), not for scripts, styles or connections. The app learns that host from its own deployment (the bucket and region it already uses for presigned URLs), never from request input; the value is a fixed hostname, not a wildcard.
- The Lambda platform is trusted to deliver the app's responses unchanged; responses the platform generates itself (timeouts, throttles, platform errors) are outside the app's control and carry no app headers.
- The Lambda function URL serves only HTTPS; `Strict-Transport-Security` applies to its hostname and subdomains. The function URL hostname changes on rebuild (known gap), which does not affect the header values.
- The web build (Vite) is trusted to emit only same-origin script and stylesheet files with no inline code.

## Out of scope
- `Cache-Control` on any response (explicitly excluded by the owner). SR-004 requires `Cache-Control: no-store` only on API responses with user-specific data; the app has no users and no user-specific data (`docs/architecture.md`, "Data").
- CORS: no allowed origins are defined, so no CORS headers are sent.
- Headers on the S3 presigned image responses themselves (served by S3, not by the app).
- Responses generated by the Lambda platform outside the app's code (timeouts, throttles, platform 5xx).
- New AWS services, IAM permission changes, or S3 public-access changes.
- A CDN, WAF or custom domain.
- Other known gaps: SR-024 log format, SR-006 timeouts, SR-027 hashed locks.
- Any change to API behaviour, response bodies or the page's look.

## Success criteria
1. For each of these requests, the response carries `X-Content-Type-Options: nosniff`, `Strict-Transport-Security: max-age=31536000; includeSubDomains` and `Referrer-Policy: no-referrer` with exactly these values: `GET /api/health`, `GET /api/dogs`, `GET /api/dogs/{breed}` for an existing breed, `GET /api/dogs/{breed}` for an invalid or unknown breed (4xx), an unknown path under `/api/` (404), an unknown path outside `/api/` (404), `GET /`, one built script asset and one built stylesheet asset.
2. A request that forces an application-level unhandled error (a 5xx produced by the app's own error handling, not by the Lambda platform) carries the same three headers with the same values.
3. Every response in criteria 1 and 2 carries a `Content-Type` matching its body; text types (HTML, JSON, JavaScript, CSS) include `charset=utf-8`.
4. `GET /` (and any other HTML response) carries `Content-Security-Policy` exactly equal to `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' https://<image-host>; connect-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'; object-src 'none'` with `<image-host>` equal to the host of the presigned image URLs returned by `GET /api/dogs`, and the value contains neither `unsafe-inline` nor `unsafe-eval`.
5. `GET /` (and any other HTML response) carries `Cross-Origin-Opener-Policy: same-origin`.
6. No response in criteria 1 and 2 carries any `Access-Control-*` header, and none carries a `Cache-Control` header introduced by this change.
7. With the change deployed, loading `/` in a browser shows the gallery with images and a working breed filter, and the browser console reports no CSP violations.
8. A test named `test_security_headers` asserts the exact values in criteria 1–6, and a ZAP baseline scan of the deployed app reports no header-related alerts (SR-004 evidence).
