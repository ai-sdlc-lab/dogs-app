## Order of work

Work in step order. Each step writes its tests in the same commit as the code, and the tests come first: they fail before the code and pass after it.

1. **A-01 to A-04 (API, `api/app/main.py`):** the header layer first, because the Content-Type table (A-02) and the CSP (A-03) are applied by it. A-04 adds only a test.
2. **A-05 (frontend):** the image-URL check and text-only rendering, plus `test_page_has_no_inline_code`. It does not depend on A-01 to A-04, but it runs after them so the CSP of A-03 is in place when the page is checked by hand.
3. **A-06 (`security.yml`):** puts the frontend test results in the JUnit file that the verifier checks for named tests. Without this step, A-05's named tests are "not found".
4. **A-07 to A-09 (`deploy.yml`):** the ZAP gate needs the release container to serve the web build (A-07). The smoke test (A-08) checks the CSP that A-03 builds. A-09 checks that the workflow hardening is still in place after A-07 and A-08.
5. **A-10:** the SR-007 limits test. Infrastructure is unchanged; the test only proves that.
6. **A-11 (EXC-001, docs):** last, because it records that the ZAP part of EXC-001 ended with A-07.

**Not in this plan (documented gaps, owner decides at the merge to `main`):** SR-005 (AUD-002, SPEC D-1), SR-006 (AUD-003, SPEC D-9) and SR-022 S3 TLS-version deny (AUD-004, SPEC D-3). INT-0002 item 7, item 8 and its out-of-scope list block them (session decision S-1). No step changes error bodies, S3 client timeouts or retries, status codes or the bucket policy.

## Test plan

- **Where the tests run:**
  - `api/tests/test_headers.py` runs with `make test-api`, in `ci.yml` job `api` and in `security.yml` job `tests`.
  - `web/test/render.test.mjs` runs with `make test-web` (`npm --prefix web test`, Node ≥ 22.18 locally, Node 24 in CI), in `ci.yml` job `web` (required check `build-and-test`) and in `security.yml` job `tests` (A-06). There the JUnit testcase names are the `test(...)` titles, which are exactly the named tests.
  - `tests/process/test_deploy.py` runs with `make test-process` and in `security.yml` job `tests`.
  - All named tests end up in the merged `junit.xml` that `named_tests.py` checks.
- **Fixture (A-01):** the web build is the SPEC 9 fixture written to `tmp_path`, not the real `web/dist`, so the API tests need no Node build. `FakeS3` is reused. `test_csp_image_host_matches_presigned_url_host` uses the real boto3 signer with dummy credentials, like `test_presigned_urls_use_regional_endpoint`.
- **Parametrisation:** `test_security_headers` is parametrised over every request in SPEC 9, with its expected status, `Content-Type` (or none) and whether CSP and COOP are expected. For each case it asserts `len(response.headers.get_list(name)) == 1` for every 1.2 header (and every 1.4 header on HTML responses), and that no `Access-Control-*` or `Cache-Control` header is present.
- **Altered MIME table (`test_content_type_exact_per_asset_type`):** `monkeypatch` sets `mimetypes.types_map` / `mimetypes.add_type` entries to wrong types for `.js`, `.css`, `.png`, `.ico`, `.svg` and `.html`. The test then requests each asset.
- **Workflow tests (`tests/process/test_deploy.py`):** they parse `deploy.yml` and `security.yml` with `yaml.safe_load` (the existing `wf` helper in `conftest.py`) and look at job keys and step `run` text. These are structural checks; the behaviour is proven on the release.
- **Release evidence (not unit tests):**
  - The `zap-report` artifact of the release run has no alert from 10019, 10020, 10021, 10035, 10038 or 10055 (the gate of A-07 enforces this).
  - The post-deploy smoke test of A-08 passes against the deployed function URL.
  - Manual, after deploy: load `/` in current Chromium and Firefox. The gallery shows images, the breed filter changes the grid, and the console shows no CSP violation (INT criterion 7).
- **Unchanged tests that must still pass:** `test_health`, `test_lists_only_well_formed_keys`, `test_by_breed`, `test_unknown_or_invalid_breed_is_404`, `test_no_api_docs_exposed`, `test_presigned_urls_use_regional_endpoint`, `test_deploy_needs_dast`, `test_verify_job_permissions_minimal`, `test_no_workflow_uses_anthropic_or_claude_action`.
- **Lint:** `ruff check` and `ruff format --check` on `api/`, and `npm run typecheck` on `web/` (`src/render.ts` is inside the `tsconfig` `include`; `web/test/` is plain JS and outside it).

- CI: `deploy.yml` (A-07 to A-09), `security.yml` and `ci.yml` (A-06) change. No new action, tool, image, secret or permission. `actions/setup-node` and `actions/download-artifact` are already pinned in this repo's workflows, and `jq` is already on the runner.

## Rollout and rollback

- **Rollout:** the code PR merges into `feature/0002-security-headers`. The owner's merge of the feature branch to `main` starts `deploy.yml`: build, then `dast` (ZAP on `/` and `/api/health`; any alert from an SR-004 header rule stops the deploy here), then deploy, then the smoke test of the real headers and CSP host.
- **Failure before deploy** (ZAP gate): nothing is deployed and the running version stays.
- **Failure after deploy** (smoke test): the workflow fails and the new version is live. If the CSP host is wrong, images don't display (fallback CSP, fail closed) and nothing else is weakened.
- **Rollback:** the owner reverts the merge commit on `main` (a PR, owner-approved), and `deploy.yml` deploys the previous build. Agents never merge to `main` or run `make apply`. No data or infrastructure migration is involved, so a rollback has no side effects beyond removing the headers again.
- **After release:** do the manual browser check (Test plan) and keep the `zap-report` artifact (30 days) as SR-004 evidence.
